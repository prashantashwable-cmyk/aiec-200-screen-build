# AIEC: what stands between the app and 90% automatic

*Gap analysis, 2026-09-27, taken at screen 067 of 200. The findings come from reading `src/data/*`
and the specs, not from the screen list.*

---

## The one-sentence diagnosis

**The app can *configure* automation but has nothing that *runs* it.** There are 67 screens
for setting up and monitoring rules, and no clock, event bus or worker that carries the rules out.
Today, if nobody opens the app, nothing happens.

Everything below follows from that.

---

## Layer 1: what you asked, the workflow gaps

### 1.1 Automation that exists only as configuration (verified in code)

| What the UI promises | What the code actually does | Where |
|---|---|---|
| Stage trigger rules (059) fire when a lead enters a stage | `updateLead` logs a timeline event and recomputes scores. **No trigger rule is evaluated.** Only `simulateTriggerRules` reads them. | `memoryRepository.ts` `updateLead`, `simulateTriggerRules` |
| Automated sequences (052) send nudges on day N | No code steps through a sequence. `sequencePausedUntil` is **written** when an agent replies but **never read**. | `sendAgentMessage` |
| Follow-up tasks are "auto-generated by the stage rule engine" (`FollowUpTask.source: 'auto'`) | The only automatic task is the revisit reminder when a lead is marked Lost. Every other `auto` task is seed data. | `markLeadLost` |
| Overdue follow-ups escalate | Nothing checks `dueDate`. An overdue task stays open forever, and no one is told. | none |
| Alerts (019, 029) are raised by SLA breaches and failures | **No code creates an `Alert`.** They are all seeded. Rule `a-5`, "Escalate SLA breach to admin", has no code behind it. | `seedAlerts` |
| Automation Health (027) shows runs and failures | `runsToday`, `failuresToday` and `lastRunAt` are seeded constants. Nothing increments them. | `seedAutomations` |
| Activity feed (012) shows what happened | Nothing appends to `activity`. The feed is a fixed snapshot. | none |
| Quotation delivery reports its result (068) | `sendQuotation` always records `delivered` and uses `quotationTemplates[0]`. | `sendQuotation` |
| Customer accepts the quote, and the deal starts | `acceptQuotation` only sets `status: 'accepted'`. **No Deal, payment schedule, job or PO is created, and the lead doesn't move to Won.** | `acceptQuotation` |
| Sequence `restartOnReopen` is an explicit choice | `reopenLead` never reads it. | `reopenLead` |

A few things are real automation and should be kept as the pattern to copy: sending a quote moves
the lead to Quoted, an interested call moves the lead up one stage, follow-ups are cancelled when
a lead closes (`reconcileFollowUpTasks`), urgent discounts inside the buffer are approved
automatically, and scores are recomputed when a stage changes.

### 1.2 Hand-offs that break across the lifecycle

The business runs as a relay: Lead → Contact → Site visit → Quote → Negotiate → Contract → Advance
payment → PO → Delivery → Install → QC → Handover → AMC → Referral. Each hand-off must answer
**who owns the next step, by when, and what happens if it doesn't happen.**

| Hand-off | Next owner assigned automatically? | Deadline set? | If missed? |
|---|---|---|---|
| Lead captured → first contact | ✅ the surveyor who captured it | ❌ | ❌ |
| Lead unassigned (import, web) | ⚠️ `suggestAssignee` exists, but a person has to accept it | ❌ | ❌ |
| Contacted → site visit | ❌ | ❌ | ❌ |
| Site visit → quote draft | ❌ nothing drafts a quote when the spec is complete | ❌ | ❌ |
| Quote sent → customer response | ⚠️ seed tasks only | ❌ validity date isn't treated as a deadline | ❌ no reminder before the quote expires |
| Discount requested → decision | ✅ goes to the admin | ❌ | ❌ a request can stay pending forever |
| **Accepted → Deal** | ❌ **the chain stops here** | | |
| Deal → contract → advance → PO → delivery → install → QC → handover | Specs 071–140 are not built. Each one must be designed as an **event consumer** of the step before it, not as a screen someone opens. | | |
| Handover → AMC renewal → referral | Specs 139, 178, 179 | | |

**What matters:** the spec for each module describes the module itself. None of them owns the
connections *between* modules. Those connections are where "90% automatic" succeeds or fails.

## Layer 2: what you meant, the app as manager and assistant

A human manager does five things. The app needs a mechanism for each, and at the moment it has
none of the five as shared infrastructure:

| A manager… | The mechanism the app needs | Status |
|---|---|---|
| **notices** that something happened | **Event bus.** Every state change emits a `DomainEvent` (`lead.stage_changed`, `quote.accepted`, `payment.overdue`…) | ❌ Changes are silent `patchInPlace` calls |
| **notices** that something *didn't* happen | **Clock / scheduler.** A `tick()` that looks for overdue items, expiring quotes, SLA breaches and due sequence steps | ❌ No clock. The only timers are UI polling |
| **gives a person a job** | **One universal `WorkItem`** with owner, due date, priority, a link to the record, and done-criteria | ⚠️ `FollowUpTask` covers leads only. Alerts, discount requests, reply-inbox items and site-visit checks are separate queues with separate rules |
| **chases** | **Escalation ladder.** Reminder → reassign → escalate to backup → alert the admin, each on its own timer | ❌ Specs 184/185 describe this. Nothing runs it |
| **reports** | **Daily brief per person.** "Your 6 things today", plus a morning check for the admin (193) | ❌ |

### The shape of the engine

It fits the existing architecture: one module behind `Repository`, with no screen changes needed
to start.

```ts
// src/data/types.ts
interface DomainEvent { id: string; type: string; entityId: string; actorId: string | 'system';
                        at: string; payload: Record<string, unknown>; idempotencyKey: string }

interface WorkItem {
  id: string; kind: 'follow_up' | 'approval' | 'reply' | 'verification' | 'exception' | …;
  entityType: 'lead' | 'quotation' | 'deal' | 'job' | 'payment' | …; entityId: string;
  ownerId: string; backupOwnerId?: string;
  dueAt: string; priority: 'critical' | 'high' | 'normal';
  status: 'open' | 'snoozed' | 'done' | 'cancelled' | 'escalated';
  escalationLevel: 0 | 1 | 2 | 3;
  /** Auto-closes when this becomes true, e.g. lead.stage >= 'site_visit'. */
  doneWhen?: { entity: string; field: string; op: string; value: unknown };
  createdBy: 'rule' | 'human'; ruleId?: string; titleKey: string; params: Record<string, string>;
}

// src/data/repository.ts
emit(event): void                // every mutating method calls this
tick(now: Date): TickReport      // scheduler: sequences, SLAs, expiries, escalations
listMyWork(userId): WorkItem[]   // the one inbox every role opens first
```

The in-memory repo drives `tick()` from a dev clock with a "fast-forward 1 day" control, so the
whole relay can be tested in the browser. In production, the same function runs from a Firebase
scheduled function (every 5 minutes) and Firestore `onWrite` triggers. **A browser cannot be the
engine: when the phone is locked, nothing runs.**

### "Done" has to be detected, not declared

A manager does not ask "did you call him?" They check whether the lead moved. `doneWhen` closes a
work item when the **business state changes**, not when someone ticks a box. That removes most of
the manual "mark complete" clicks, and removes the fake completions too.

## Layer 3: what you didn't know to ask

### 3.1 "Run by one person" and "multiple users" contradict each other in the current model

- `Role` has 5 values: admin, surveyor, technician, customer, supplier. But
  `000_INFORMATION_ARCHITECTURE.md` gives screens to **Sales (24 mentions), QC Inspector, Support
  and Manager**, and none of these roles exist. Today every sales, approval and QC action has to be
  done by the one admin, which makes the admin the bottleneck. That is the opposite of automation.
- **Approvals can't be separated.** Only one admin exists, so on a discount request the requester
  and the approver can be the same person. Money controls need four eyes, or at least a
  "self-approval is logged and flagged" rule.
- **The owner is a single point of failure.** Spec 193 raises this. The fix is data, not UI: every
  `WorkItem` gets a `backupOwnerId`, and there is an out-of-office flag that reroutes work.
- Actions are recorded with hard-coded actor names (`'Sales'`, `'Customer'`, `'Automation'`)
  instead of the session user. A multi-user audit trail (187) can't be built on that.
- **Permissions are enforced only by which screens the UI shows.** The repository does not check
  who is calling it. With Firebase, that becomes Firestore security rules. Design them per role
  now, while there are 5 entities, not at screen 192 when there are 60.

**Decision needed:** add `sales` and `qc_inspector` to `Role` (and probably `accounts`) **before**
building Module 8. Negotiation, contracts and payments all assume someone other than the owner
does the work.

### 3.2 Automations will contradict each other

Once the engine runs, a single lead entering "Quoted" could trigger all of these at once: a 059
trigger rule, a 052 sequence, a 056 bot reply, an auto follow-up call task, a 083 payment reminder
later, and a 055 broadcast. The customer would get 4 messages in an hour. The app needs:

- **A contact-level frequency cap** across *all* channels and modules, e.g. at most 1 outbound
  message per 24 h and 3 per week, except transactional messages.
- **A single outbound gateway.** Every automated message goes through one `dispatch()` that checks
  opt-out, the cap, quiet hours (no messages from 9 pm to 9 am), a human conversation in progress
  (`sequencePausedUntil`), and deduplication.
- **Idempotency keys** so a retried tick never sends twice, and no WorkItem is created twice.

### 3.3 Indian regulations constrain the automation, and the specs don't mention them

- **SMS requires TRAI DLT registration.** Every SMS template must be pre-registered with an entity
  ID and a header, or operators block it. Free-text SMS broadcasts (055) won't deliver as designed.
  `CommTemplate` needs `dltTemplateId`.
- **WhatsApp Business API:** outside the 24-hour customer-service window you can only send
  **Meta-approved templates**. An automated nudge on day 5 must be an approved template, not free
  text. Model `approvalStatus` per template.
- **DPDP Act 2023:** consent has to be recorded per purpose (marketing is separate from
  transactional), along with erasure requests. The opt-out ledger (058) is a good start. Connect it
  to 194.
- **GST e-invoicing** applies above the turnover threshold (087/116): invoices need an IRN from the
  IRP. That is an external dependency that can fail, so it needs a retry queue.

### 3.4 Define "90%" or it will never be reached

Put one metric on 193 and 027:

> **Automation rate** = the share of workflow transitions that happened without a human action.
> Measured from `DomainEvent.actorId === 'system'` per hand-off.

Then show the **top 5 hand-offs that still need a human**, ranked by volume. That list becomes the
backlog. The Manual Override log (188) belongs in the same view: an override that keeps happening
means the rule needs to change.

### 3.5 Automation needs brakes

- A **global kill switch** and a **per-rule dry-run mode**, where the rule logs what it *would*
  have done for a week before it goes live. Spec 190 (sandbox) should be the default state of every
  new rule, not a separate screen.
- **Blast-radius limits.** For example, a rule that wants to message more than 50 contacts or move
  more than ₹X in one tick pauses and asks the admin.
- Money-moving actions (payouts, refunds, supplier payments) stay **human-approved** permanently.
  The approval is automated up to the button press. That is how the remaining 10% should be spent.

### 3.6 The build order works against the goal

The plan builds 200 screens in number order and the engine arrives at 181–190. Every screen from
068 to 180 will add configuration that nothing executes, and each one will then need rework to
connect to the engine. **Build the engine now, before 068**, and make each later screen an event
producer or consumer from its first commit. Spec 068 is a good first client: a scheduled send, a
WhatsApp bounce that falls back to email, and cancellation when the quote is superseded all need
the scheduler.

### 3.7 Nothing is persisted

The in-memory store resets on every reload, which suited the demo. But multi-user means two people
editing the same lead, so records need `version` fields for optimistic concurrency ("Ravi changed
this lead 2 minutes ago. Reload?"). Add `version` to `Lead`, `Quotation` and `WorkItem` now.

## Recommended plan

**Phase 0: engine core (before 068, about 3 commits, no new screens)**
1. `DomainEvent` + `emit()` called from every mutating repository method; an `activity` feed and a
   timeline built from events (so 012 goes live).
2. `WorkItem` (generalise `FollowUpTask`; keep it as a view) + `doneWhen` auto-close + `listMyWork`.
3. `tick(now)` + dev fast-forward control: evaluate 059 trigger rules, advance 052 sequences
   (respecting `sequencePausedUntil`, caps and opt-out), raise SLA `Alert`s, escalate overdue work,
   and increment `AutomationRule` run counters (so 027 goes live).

**Phase 1: close the broken chain**
4. `acceptQuotation` → create a Deal, move the lead to Won, create a payment schedule WorkItem for
   Accounts. Automatic reminder before the quote validity expires.
5. Auto-draft a quote when a lead's spec is complete and the site visit is verified.
6. Routing through `suggestAssignee` applied automatically, with a person overriding it rather than
   approving it.

**Phase 2: people**
7. Add the `sales` and `qc_inspector` roles, `backupOwnerId`, out-of-office, separation of approval
   duties, and the session user as the actor everywhere.
8. A "My Day" home screen per role, built on `listMyWork`, plus the admin morning brief (pull 193
   forward).

**Phase 3: production**
9. Firebase scheduled functions and triggers running the same `tick`/`emit` code, Firestore
   security rules per role, a `dispatch()` gateway with DLT and WhatsApp template compliance.

Phases 0–2 work within the current rules: in-memory, no secrets, three languages. Phase 3 is the
first time the repo needs a real backend project.
